## Findings and follow-ups

- **Planted data problems behave as designed on Fabric.** The nightly build ends with 2 errors: yield > 100%, which also skips the 7 `fct_batch` nodes, and the missing ND excise rate in gold. It also gives 6 warnings: late distributor, 37 invoice lines without a shipment, 14 unmapped Northland SKUs, an unknown state spelling, a missing excise rate in silver, and 3 unmapped SKU groups in gold. `.\tasks.ps1 build` therefore exits 1 in the "act 1" state.
- **A fresh environment needs a special first build**, also for the Fabric dbt job (phase 6/7). **Corrected 2026-11-15:** the `--empty` bootstrap in item 8 only works when the incremental model's parents exist (it was proven by dropping `fct_sales_line` alone). In an empty warehouse, `snap_erp_customer`, `dim_brand` and the seeds are missing too. Building them with `--empty` is not safe: the snapshot uses `invalidate_hard_deletes`, so in an existing environment an empty run would close every customer's history. The first build is therefore `.\tasks.ps1 build -FirstBuild`: everything except unit tests, then the unit tests. The job can't run that sequence in one command, so `deploy.py` runs it from the local venv once, before the first job run in Test/Prod. Not yet run against an empty warehouse: the reset that would prove it (`.\tasks.ps1 reset -Env dev -Yes`) is waiting for the user to run it.
- **`--empty` and aliased refs:** `dbt run --empty` wraps each ref as `(...) AS _dbt_limit_subq`, so `{{ ref('x') }} as y` breaks. Fixed in `fct_sales_line`. `fct_channel_inventory_monthly` and `tests/singular/assert_excise_rate_for_every_sales_state.sql` still alias refs directly. Change them to import CTEs before using `dbt build --empty` (for example in CI).
- **Python:** the job runtime is Python 3.12; local stays 3.11 (CLAUDE.md). No difference observed.
- **Proposed DESIGN.md updates** (not made here, because DESIGN.md has uncommitted edits in the working tree): §7 venv line → dbt-core 1.11 / dbt-fabric 1.10.0 + ODBC Driver 18; §10 last bullet (mssql-python) → answered: not on the runtime version; §4 orchestration → add the SQL endpoint refresh step, and note freshness can't run as a dbt job operation; §5 macros → add `drop_dbt_tmp_relations.sql`.
- **The job's definition holds environment IDs** (workspace, warehouse, SQL endpoint). Once Dev is git-synced, `fabric/dbt_lpb.DataBuildToolJob/dbt-content.json` will contain Dev's IDs, and fabric-cicd would need `parameter.yml` replacements for them (item 13). `dbt_job.py` avoids this by building the definition for each environment. The git-synced `Code/dbt/` would also be a second copy of `dbt/`.
- **The job also prints the "Nested CTE warning"** (item 5) for unit tests. It is harmless, but it fills the job's truncated failure message, so read `Output/<run>/logs/dbt.log` for the real errors.
- **Fabric items in `LPB-Data-Dev`:** `lh_bronze`, `wh_analytics` (+ schemas), `nb_ingest_bronze`, `dbt_lpb` (configured once in the UI, now deployed by `dbt_job.py`). The spike copy of the dbt project in `lh_bronze/Files/dbt/lpb` was deleted. Nothing was created outside `LPB-Data-Dev`.
- **IDE:** the VS Code YAML schema flags `data_tests:` and `unit_tests:` as "not allowed". The schema is outdated; dbt parses these files without warnings.
