# Fabric + dbt Demo — Design (v0.3.1)

**Status:** design approved; scaffold, data generator and dbt skeleton built; spike next · **Owner:** Jon Messier · **Last updated:** 2026-11-12
**Repo:** `github.com/JMFultonAnalytics/dbt-tutorial` → local `C:\Dev\dbt-tutorial` (Windows, Python 3.11, PowerShell)
**Guiding principle:** build it the way a real client would run it: real-looking source systems, daily loads, history tracking, data contracts, CI/CD, dev/test/prod. The dbt features are the stars, but each one shows up because the business needs it, not as a toy example.

Changes from v0.3: ERP price list is effective-dated, so only customers need a snapshot; one generator script with `backfill` and `advance` subcommands; `ref_distributor` seed and `scripts/load_env.ps1` added; history lands as a full extract dated the business date.

Changes from v0.2: domain, silver engine, environments, capacity and identity decided (full tenant admin available); added `setup_identity.ps1` and tenant-settings prerequisites.

## 1. Goals

1. **Modular builds**: run one seed, one model, a model plus upstream/downstream, a layer, or only what changed.
2. **Unit tests**: prove business logic (margin, SKU mapping, fiscal calendar, SCD logic) with fixed inputs.
3. **Warnings vs errors, reviewable**: freshness and data tests that warn or fail by severity or threshold; results land in logs, `run_results.json`, and an `audit` schema in the Warehouse.
4. **Medallion**: Bronze (raw, as landed) → Silver (dbt: cleaned, conformed, history) → Gold (dbt: star schema, contracted).
5. **Gold feeds a semantic model** (phase 8).
6. **Scripted and Claude-friendly** end to end.

## 2. The business

**Larkspur & Pine Brewing Co.** (fictional), a regional craft beverage manufacturer in the Upper Midwest. About 60 SKUs (beer, seltzer, NA) in kegs, cans and bottles. Three channels:

| Channel | How it works | Revenue recognized from |
|---|---|---|
| **Wholesale (3-tier)** | sells to 3 distributors in MN/WI/IA, who sell to retailers and bars | ERP invoices (shipments to distributors) |
| **Taproom** | on-site sales | POS transactions |
| **Direct / events** | festivals, private events, metro self-distribution | ERP invoices |

### Business questions Gold must answer
1. Revenue, volume (barrels and cases) and **gross margin** by SKU, channel, region, fiscal period.
2. **Shipments vs depletions**: sold *to* distributors vs sold *through* to retailers → weeks of inventory in the channel.
3. **Price realization**: invoiced price vs list price in effect on the invoice date (needs price history).
4. **Production**: batch yield and loss %, cost per barrel, packaging efficiency.
5. **Account performance**: top and declining retail accounts (from depletions), new vs lost accounts.
6. Excise tax liability by state (rates are reference data).

## 3. Source systems (simulated) → Bronze

All generated by `scripts/generate_data.py` (deterministic random seed). Files land in a **landing zone** by system and date, like a real ingestion setup.

| # | System (stand-in for) | Feed | Format & cadence | Bronze tables |
|---|---|---|---|---|
| 1 | **ERP** (Business Central-style) | customers, items, price list, sales orders, order lines, shipments, invoices | CSV, daily incremental (changed rows) | `erp_customer`, `erp_item`, `erp_price_list`, `erp_sales_header`, `erp_sales_line`, `erp_shipment`, `erp_invoice_line` |
| 2 | **Brewery production** (Ekos/Orchestrated-style) | batches, ingredient usage, packaging runs, batch costs | JSON, daily | `prod_batch`, `prod_ingredient_usage`, `prod_packaging_run`, `prod_batch_cost` |
| 3 | **Taproom POS** (Square/Toast-style) | transactions and line items | JSON, daily | `pos_transaction`, `pos_line_item` |
| 4 | **Distributor depletion reports** | each distributor's monthly sell-through by retail account, **in their own SKU codes and account names** | CSV/XLSX, monthly, 3 different layouts | `dist_depletion_northland`, `dist_depletion_badger`, `dist_depletion_hawkeye` |

**Landing → Bronze:** `Files/landing/<system>/<yyyy-mm-dd>/…` → notebook `nb_ingest_bronze` appends to Delta tables in `lh_bronze`, adding `_source_file`, `_ingested_at`, `_batch_id`. Bronze is **append-only and never cleaned**.

**Time simulation:** the generator builds about 18 months of history up to a "business date" and lands it as one full extract in that date's folder (distributor reports land in the folder of the day each was received). `advance-day` drops the next day's files (new orders, a customer address change, a price change, a late-arriving file), so incremental models, snapshots and freshness checks do real work during the demo.

### Realistic data problems (planted on purpose)
| Problem | Where | dbt mechanism | Severity |
|---|---|---|---|
| POS file re-sent → duplicate transactions | `pos_transaction` | dedupe in stg (unit-tested) + `unique` | error if dupes survive |
| Distributor SKU code not in cross-reference | depletions | `relationships` to seed → **fix by adding a seed row** | warn |
| Distributor file late (one distributor a month behind the others) | depletions | singular test `assert_distributor_reports_not_late`; source freshness only covers "nothing loaded for 35/45 days" | warn |
| ERP feed not refreshed today | `erp_*` | `source freshness` on `_ingested_at` | warn 26h / error 50h |
| Invoice line with no matching shipment | ERP | relationships test | warn |
| Returns as negative qty | ERP | **valid**, modeled as credit, unit-tested | none |
| Batch yield > 100% (data-entry error) | production | custom test `between(0, 1.0)` | error |
| Missing excise rate for a state we ship to | seed | relationships | error |
| Customer moved or changed tier mid-year | ERP customer | snapshot (SCD2) | none |
| List price change mid-period | ERP price list (effective-dated: `starting_date`, `ending_date`) | point-in-time join, unit-tested | none |

## 4. Platform architecture

```
 Landing (Files)      BRONZE                 SILVER                    GOLD                     (Phase 8)
 erp/ prod/ pos/  →  lh_bronze (Lakehouse) → wh_analytics.silver  →  wh_analytics.gold     →  Semantic model
 dist/            nb_ingest_bronze         stg_*, int_*, snapshots   dim_*, fct_* (contracted)   (Direct Lake)
                                           ▲ dbt (dbt-fabric)        ▲ dbt
                  seeds → wh_analytics.ref     audit schema: test failures + run log
```

### Decisions
| Decision | Choice | Rationale |
|---|---|---|
| Bronze | **Lakehouse** `lh_bronze`, Delta, append-only | standard Fabric landing pattern; notebook ingestion of JSON/CSV |
| Silver + Gold | **Fabric Warehouse** `wh_analytics`, schemas `ref` (seeds), `silver`, `snapshots`, `gold`, `audit` | `dbt-fabric` is the mature adapter, and Fabric's native **dbt job only supports Warehouse**; T-SQL is familiar to client teams |
| Silver on Lakehouse via `dbt-fabricspark` | **Not in v1**; optional "Act 2" | Spark session startup is slow for a live demo, and the dbt job can't run it |
| dbt reads Bronze | `sources:` over the lakehouse SQL endpoint, three-part names | no copy; lineage starts at Bronze |
| Packages | none in v1 (own generic tests and macros) | dbt job preview package limitation; revisit `dbt_utils` after spike |
| Gold stability | **model contracts** on `dim_`/`fct_` + `exposures:` for the semantic model | protects the semantic model from breaking changes |

### Workspaces and environments
| Workspace | Contents | How it's updated |
|---|---|---|
| `LPB-Data-Dev` | `lh_bronze`, `wh_analytics`, `nb_ingest_bronze`, `dbt_lpb` (dbt job), `pl_daily_load` | Git-synced to `main` (folder `fabric/`); developers run dbt locally against it |
| `LPB-Data-Test` | same | `fabric-cicd` on merge to `main` |
| `LPB-Data-Prod` | same | `fabric-cicd` after manual approval |
| `LPB-Analytics-<env>` *(phase 8)* | semantic model, reports | separate BI workspace |

One capacity hosts everything (name set in `config/environments.yml`; `provision.py` lists available capacities if unset). Scripts take `-Env dev|test|prod`; Dev is built first.

### Orchestration (`pl_daily_load`)
`nb_ingest_bronze` → **dbt job activity**: `dbt source freshness` → `dbt build --selector nightly` → on failure, Teams/email → (phase 8) semantic model refresh.

## 5. dbt project

```
dbt/
  dbt_project.yml  profiles.yml (env-var driven, no secrets)  selectors.yml  .sqlfluff (tsql)
  seeds/   ref_distributor.csv  ref_distributor_sku_xref.csv  ref_distributor_account_xref.csv  ref_channel.csv
           ref_state_region.csv  ref_excise_tax_rate.csv  ref_fiscal_calendar_445.csv  ref_uom_conversion.csv
  snapshots/  snap_erp_customer.sql   (the ERP keeps no customer history; the price list is already effective-dated)
  models/
    staging/erp/ prod/ pos/ dist/     _<system>__sources.yml (with freshness)  stg_<system>__<entity>.sql
    intermediate/  int_sales_lines_unioned (ERP + POS)  int_depletions_unioned (3 layouts → 1)
                   int_depletions_mapped (xref)  int_batch_cost_per_unit  int_invoice_price_vs_list
    marts/core/    dim_date  dim_product  dim_account (SCD2)  dim_distributor  dim_channel  dim_geography
           sales/  fct_sales_line (incremental)  fct_shipments  fct_price_realization
           channel/ fct_depletion  fct_channel_inventory_weekly
           production/ fct_batch  fct_packaging_run
  tests/generic/  between.sql  non_negative.sql  valid_date_order.sql
        singular/ assert_gold_revenue_reconciles_to_erp.sql  assert_no_unmapped_skus_in_gold.sql
  macros/  generate_schema_name.sql  log_run_results.sql  to_barrels.sql  fiscal_period.sql
  analyses/
```

### Layer rules (mirrored in CLAUDE.md)
- **stg_<system>__<entity>**: 1:1 with a source; rename, cast, trim, dedupe, standardize units. No cross-source joins. Views.
- **int_**: unions, mappings, business logic. Ephemeral or views. Not exposed to BI.
- **gold dim_/fct_**: star schema, surrogate keys, business-friendly names, **contract enforced**, documented. The only layer the semantic model reads.
- Every model: YAML description + tests. Every int_/fct_ with arithmetic or mapping: unit test. Every source: freshness.

### Feature showcase map
| dbt feature | Where it shows up for a real reason |
|---|---|
| **Seeds** | distributor SKU/account cross-references, excise rates, 4-4-5 fiscal calendar: business-owned reference data in git |
| **Run one / in series** | `dbt seed -s ref_distributor_sku_xref` → `dbt build -s ref_distributor_sku_xref+` after fixing an unmapped SKU |
| **Sources + freshness** | each system has freshness SLAs; a late distributor file warns, a stale ERP feed errors |
| **Unit tests** | dedupe, returns as credits, barrels conversion, depletion layout normalization, price-in-effect join, 4-4-5 period logic, incremental filter |
| **Data tests + severity** | warn/error thresholds per §3; `store_failures` → `audit` |
| **Snapshots (SCD2)** | customer tier/territory changes (the ERP overwrites them); price realization uses the effective-dated price list |
| **Incremental** | `fct_sales_line` merges new days; `--full-refresh` when logic changes |
| **Contracts** | gold columns and types locked; a breaking change fails the build before it reaches Power BI |
| **Exposures + docs** | semantic model declared as an exposure; lineage from landing file to report |
| **Selectors / state** | `nightly`, `production_only`, `state:modified+` in CI |
| **Hooks** | `on-run-end` writes `audit.dbt_run_log` |

### Demo selection commands
| Show | Command |
|---|---|
| One seed | `dbt seed -s ref_distributor_sku_xref` |
| Fix flows downstream | `dbt build -s ref_distributor_sku_xref+` |
| One model | `dbt run -s stg_pos__transaction` |
| Upstream of a fact | `dbt build -s +fct_depletion` |
| One source system end to end | `dbt build -s source:pos+` |
| A layer | `dbt build -s tag:gold` |
| Freshness | `dbt source freshness` |
| Unit tests only | `dbt test -s test_type:unit` |
| Only what changed | `dbt build -s state:modified+ --defer --state .\prod-artifacts` |
| Rebuild incremental | `dbt run -s fct_sales_line --full-refresh` |

### Reviewing warnings and errors
Console → `dbt\logs\dbt.log` → `target\run_results.json` / `sources.json` → `audit.dbt_run_log` + `audit.<test>` failure tables → Fabric dbt job Output tab / Monitoring hub → (optional) a small "Data Quality" report on the audit schema.

## 6. Identity, tenant settings and CI/CD

Jon has full admin on the demo tenant, so all of this is scripted.

### Tenant settings to enable (admin portal; `setup_identity.ps1` prints the checklist and verifies what it can via API)
- dbt job (preview)
- Service principals can use Fabric APIs (scoped to a security group `sg-lpb-fabric-automation`)
- Users can synchronize workspace items with their Git repositories (GitHub)
- Users can create Fabric items

### Identity (`scripts/setup_identity.ps1`, Azure CLI)
- Entra app `app-lpb-fabric-cicd` + service principal, added to `sg-lpb-fabric-automation`.
- GitHub OIDC federated credentials for `repo:JMFultonAnalytics/dbt-tutorial:environment:test` and `:prod` and `:pull_request` (no client secrets).
- Workspace roles: Contributor on Test/Prod (deploy), Contributor on Dev (CI builds into throwaway schemas).
- Outputs tenant ID / client ID to `.env` and prints the `gh secret set` / `gh variable set` commands (or runs them if `gh` is logged in).

### GitHub Actions
| Trigger | Workflow | Does |
|---|---|---|
| Pull request | `ci.yml` | sqlfluff lint · `dbt parse` · `dbt build -s state:modified+ --defer` into a throwaway `ci_pr<N>` schema in Dev warehouse · post summary of warns/errors to the PR · drop schema |
| Merge to `main` | `deploy.yml` (test) | `fabric-cicd` publish to `LPB-Data-Test` · run pipeline · upload `manifest.json` artifact (state for next CI) |
| Manual approval | `deploy.yml` (prod) | same, to `LPB-Data-Prod` |

Local dev uses `az login` (dbt-fabric `authentication: CLI`).

## 8. Demo storyline (~40 min, can be cut to 20)

1. **The business and the mess**: Larkspur & Pine's questions; peek at landing files: three distributor layouts, dupes in POS.
2. **Lineage**: `dbt docs`: landing → bronze → silver → gold → semantic model exposure.
3. **A new day arrives**: `advance-day`; `dbt source freshness` (one distributor late → warn); `dbt build --selector nightly`: incremental fact adds rows, snapshot records a customer move.
4. **Reference data is code**: unmapped distributor SKU warning → add one row to the xref seed → `dbt build -s ref_distributor_sku_xref+` → warning gone, depletions reconcile.
5. **Unit tests protect the margin math**: break returns handling → red unit test with diff → `build` refuses to materialize → fix.
6. **Errors stop the line**: batch yield 140% → error → downstream production facts skipped, sales still built; query `audit.dbt_run_log`.
7. **Contracts**: rename a gold column → build fails before Power BI breaks.
8. **Native in Fabric + CI/CD**: open a PR → CI comment with results → merge → deploy to Test → pipeline runs the dbt job → Monitoring hub.
9. *(Phase 8)* Semantic model and report on Gold.

## 10. Spike checklist / risks

- dbt job runtime version in tenant → pin local `dbt-core`/`dbt-fabric` to match (local is 1.12 today).
- `unit_tests:` and **model contracts** on Fabric Warehouse with that adapter version.
- **Snapshots** on Fabric Warehouse (`timestamp` strategy) at that version.
- Three-part-name sources to `lh_bronze` from both local runs and the dbt job runtime.
- `dbt source freshness` inside the dbt job / pipeline activity.
- Packages in dbt job (if allowed, add `dbt_utils` later).
- How the dbt job item is represented in Git; `fabric-cicd` deploy of `DataBuildToolJob` with `parameter.yml` swapping the warehouse connection.
- Programmatic trigger of the dbt job (pipeline run API is the fallback).
- Service principal + GitHub OIDC permissions on Fabric workspaces.
- `mssql-python` driver bundled with dbt-fabric 1.11: confirm no separate ODBC install needed.
